## 1. Az ellenőrzés módszere és korlátai

A GitHub API által szolgáltatott `main` Git-fát, a fő konfigurációkat, dokumentációt,
workflow-kat és a branch/Actions állapotot ellenőriztük. A Git-fát az API nem jelezte
csonkoltnak (`truncated=false`).

Az ellenőrzés környezetében **nincs `rustc` és `cargo`**, és a GitHub git-protokoll szerinti
lekérése DNS-hiba miatt nem lehetséges. Ezért **nem futott**:
`cargo metadata`, `cargo build`, `cargo xtask ci`, oracle teszt, Linux GUI,
valódi GPU- vagy import/export futtatás. Az itt felsorolt forrás- és konfigurációs tények
**nem egyenértékűek** a sikeres működési teszttel.

## 3. Meglévő ellenőrzések (forrásvizsgálattal igazolva)

Az [xtask/src/main.rs](../../xtask/src/main.rs) `ci()` függvénye az alábbiakat hívja:

1. `cargo fmt --check`;
2. `cargo clippy --workspace --all-targets --release -- -D warnings`;
3. `cargo test --workspace --release`;
4. belső `layers()`;
5. belső `assets()`;
6. `wasm()`.

Ezek **létező parancsok**, de ennek az auditnak a keretében egyik sem futott.

A [.github/workflows](../../.github/workflows) jelenlegi fájljai:
`freebsd.yml`, `nix.yml`, `packaging-lint.yml`, `release.yml`,
`windows-arm64.yml`. Nincs minden PR-ra általánosan lefutó Rust tesztkapu.

A `nix.yml` megengedi, hogy a `flake.nix` hiánya sikeres kihagyással végződjön;
a `flake.nix` nincs a vizsgált fájlfában. Ezt követelményként vagy nem célzott
funkcióként külön kell tisztázni.

## 4. Forrásfüggőségek, márkajog, kiadás

- A `Cargo.toml` két `storytold/craft-libs` Git-függőséget tartalmaz,
  **rögzített commit SHA-val**, tehát nem lebegő `main` hivatkozások.
- A `release.yml` és több csomagolási workflow a
  `storytold/craft-common-actions` újrafelhasználható workflow-it hívja **`@main`**
  referenciával: ez változó külső kiadási függőség.
- A [docs/brand/LICENSE-brand.txt](../brand/LICENSE-brand.txt) szerint az
  ArtCraft márkajelzések nem tartoznak a szoftver MIT/Apache-2.0 licencéhez,
  és egy önálló módosított verzió terjesztésénél el kell őket távolítani vagy
  megfelelő engedéllyel kell használni.
- A Linux AppStream/Flatpak azonosítók, a macOS bundle és Windows MSI metadata
  több helyen a korábbi alkalmazás azonosítóit és a kiadó adatait használja.
- A [README.md](../../README.md) több telepítési, támogatási és kiadási URL-je
  az eredeti projekt oldalára vezet. Ezeket az önálló kiadás előtt felül kell vizsgálni.
- A `docs/roadmap.md` egy bekezdése azt állítja, hogy még nincs `cargo xtask parity`,
  miközben az `xtask/src/main.rs` már definiálja ezt a parancsot.

## 5. Nyitott futtatási ellenőrzések

Következő lépések egy **Rust 1.95-öt, cargo-t és GitHub hozzáférést tartalmazó**
fejlesztői / CI környezetben:

```bash
cargo metadata --format-version 1 --no-deps
cargo build --workspace --locked
cargo xtask ci
FILMCRAFT_REQUIRE_ORACLES=1 cargo test --workspace --release --locked
```

A futtatáskor rögzítendő: operációs rendszer és verzió, CPU/GPU, driver,
Rust toolchain, FFmpeg/ffprobe verzió, commit SHA, parancs, exit code, log,
kihagyott tesztek és reprodukciós utasítás.

A GUI-folyamatokhoz külön kell bizonyítani: indítás, import, szerkesztés, mentés,
újranyitás, export, leállás utáni helyreállítás. A média-korpuszhoz
ellenőrzőösszegek szükségesek.

## 6. F0 lezárási kritérium

Az F0 issue **nyitva marad** addig, amíg a kötelező fordítás, teszt,
oracle- és Linux GUI-vizsgálat hitelesített eredményei nem szerepelnek itt
vagy a kapcsolódó tesztjegyzőkönyvekben. A statikus audit önmagában csak
az első ellenőrzési részfeladat lezárását jelenti.

A következő javítási csomagok: F1 önállósítás, F2 CI/biztonság,
F3 stabilitás, F4 médiafeldolgozás, F5 kompatibilitás, F6 AI/lokalizáció.
